## Decisions made

- Assessment corrections use separate nested teacher-assessment and disability-information PATCH routes. Policies and the request verify both the advised learner and the exact record's learner ownership; route type fixes the record kind. The write transaction locks the school, learner and record, freshly authorizes the actor and updates only date/observations for teacher assessments or category/optional clinical details for disability records. School/learner/record IDs and the original recorder/creation timestamp cannot be changed, including empty prohibited fields. No migration/schema change was needed.
- Existing encrypted casts protect corrected observations, clinical notes, professional/clinic and diagnosis date; private fields remain hidden from automatic serialization and validation-session flashing. Each correction writes a learner/actor audit event without narrative attributes; audit failures roll back changes and error logs contain only a constant message/exception class. Reassigned advisers may correct records but do not replace the original recorder. Neither correction decides diagnosis/readiness or changes enrollment/level. Edit/Cancel controls populate each separate form; validation retains corrections, and success refreshes the cards and clears only the saved form. Browser/mobile interaction review remains pending.

- Guardian/contact editing updates only name, relationship, optional phone/email/address and the selected learner link's primary/emergency flags. Nested requests verify the contact belongs to the learner; school/learner/contact locking and fresh policy authorization protect saves. Existing parent-account and ownership fields are protected by an explicit allowlist, including empty prohibited values. Updates and learner-link flags roll back if auditing fails; audits contain event/actor/learner identifiers rather than contact attributes. No migration/schema change was needed.
- Current creation makes a separate contact record per learner. The schema also permits shared contacts; edits from a learner page are denied when the contact has more than one link, including a link hidden by adviser scope. This conservative restriction prevents changes affecting another learner without authorization/auditing. Shared-contact reuse/editing needs a separate agreed workflow. The edit form supports cancel, preserves entered corrections on validation errors and reloads saved card data after success. Browser/mobile interaction review remains pending.

- Learner names link to a detail page with identity, optional health notes, own-advised enrollment history, prior-consent confirmation date and contacts/assessment links. Edit identity changes only first/last/middle names, birthdate, sex, address, mother tongue and health notes. Both view and edit GETs are audited before releasing explicit profile data; the update transaction locks the school/learner and freshly authorizes the actor. Health notes stay encrypted and updates roll back if auditing fails. No schema change was needed.
- SMILE ID, LRN/status, school/section/year, learner/enrollment status, level, consent and PWD/photo fields are not editable through identity updates. An explicit update allowlist also discards empty prohibited fields, so nullable request values cannot clear an existing LRN. Pending-LRN addition/correction needs its own audited workflow; clarify correction handling for permanent LRNs and needs_correction before enabling replacement. Contact and assessment editing are implemented as separate audited workflows. Successful updates reload the profile so the saved values display immediately rather than retaining the old form state.

- Teacher observations/test findings use a separate teacher_assessments table rather than being stored as medical diagnoses. It records school/learner, date, encrypted observations, server-assigned teacher UUID and creation timestamp. Disability information retains schema.sql's category references with optional encrypted diagnosis_date, assessed_by and notes. Diagnosis date is now encrypted text instead of a plaintext date column. Categories are a global read-only reference catalogue from the supplied schema, not learner data; no category labels, diagnoses, grading scales or DepEd form rules were invented.
- learner_disabilities and teacher_assessments have school_id, global school/adviser scopes, model policies and same-school learner/teacher foreign keys. Schema.sql and migration changed together. /learners/{learner}/assessments allows only the advised learner's teacher, including dual-role teachers. Creation reauthorizes a fresh actor under school/learner locks and rolls back when auditing fails; viewing fails closed. Sensitive notes/provider/date fields are excluded from automatic model serialization and validation-session flashing; explicit authorized view data is released only after auditing. Category IDs and educational assessment dates remain ordinary relational metadata; clinical narrative/provider/diagnosis-date and teacher observations are encrypted.
- Missing medical documents/details do not block teacher assessment, disability information or enrollment. Teacher assessments do not create a disability diagnosis, approve readiness, or change the non-graded enrollment. Record deletion and file attachments remain pending; source forms and populated examples stay unchanged and out of Git.

- Add learner now displays the configured current school year separately from the enrollment year of the selected section. Current-year sections are marked Current; the empty-section notice links administrators to section setup. No dates/year labels are guessed and no school settings or sections are automatically created. Diagnostic check found development year 2026-2027 marked current but no sections; a section advised by the teacher is still required to save enrollment.

- Guardians and learner_guardians now carry school_id and global school/adviser access scopes; composite learner/guardian foreign keys reject cross-school links. Contact records use the existing schema's name, free-text relationship, optional phone/email/address and per-learner primary/emergency flags. They are optional and do not block enrollment. Each save creates a new contact linked only to the selected learner; contact reuse, deletion and parent portal account linking remain unimplemented. No singular-primary restriction or report-specific relationship mapping was invented.
- /learners/{learner}/guardians provides audited contact viewing and creation. Saving locks the school and learner and reauthorizes a fresh actor; contact and link roll back if auditing fails. Route binding and policies deny other advisers, schools, inactive accounts, parents and system administrators, including dual-role administrators. Audit entries reference the learner and actor with event names only; no contact attributes are copied. Contact details are excluded from validation-session flashing. SF1 parent/maiden-name mapping still needs confirmation before report work.
